Un ataque a 4.837 cuentas de GitHub inyecta robos de secretos en más de 1.800 repositorios

Investigadores de seguridad han destapado una campaña masiva contra la cadena de suministro en GitHub que utilizó credenciales robadas de 4.837 cuentas para sondear repositorios y ejecutar un ladrón de secretos en flujos de integración continua (CI) de al menos 1.806 proyectos.

Edición y revisión: Cristian Moriche · Publicada el 12 de noviembre de 2026 a las 18:58

Texto elaborado con ayuda de inteligencia artificial a partir de las fuentes citadas. Política editorial

Claves

  • Los atacantes probaron permisos de escritura abriendo pull requests automatizadas con el título «docs: dependency audit notes» desde la rama wfx-docs.
  • En al menos 1.806 repositorios lograron inyectar un script en GitHub Actions o ganchos de npm install para extraer claves de AWS, Azure, GCP y API de IA.
  • Tras robar los tokens y secretos, la automatización borraba registros y revertía cambios para ocultar el rastro de la intrusión.

Qué ha pasado

Una campaña coordinada contra la cadena de suministro de software, rastreada por firmas como Aikido Security y SafeDep bajo el nombre de wfx-loot, ha aprovechado credenciales comprometidas de 4.837 cuentas de GitHub para intentar infiltrarse en decenas de miles de repositorios donde esas cuentas tenían acceso.

Según detallan Aikido Security, The Hacker News y Help Net Security, el ataque comenzaba de forma automatizada abriendo pull requests de prueba tituladas «docs: dependency audit notes» desde una rama llamada wfx-docs para comprobar si la cuenta secuestrada tenía permisos de escritura directa.

Publicidad

Qué robaban y cómo ocultaban el rastro

En al menos 1.806 repositorios, la carga maliciosa —un script de shell de unas 1.500 líneas inyectado en flujos de GitHub Actions o mediante hooks de npm install— llegó a ejecutarse. Su objetivo era recolectar secretos de entorno, tokens de acceso, credenciales en la nube (AWS, Azure y GCP) y claves API de proveedores de inteligencia artificial.

Para dificultar la detección, los atacantes revertían rápidamente las modificaciones en el código y eliminaban las ejecuciones y registros (logs) de los flujos de trabajo tras exfiltrar los datos.

Cómo comprobar si te afecta

Estos pasos son recomendación práctica basada en el comportamiento descrito por los investigadores:

  1. Revisa el historial de pull requests cerradas o recientes y busca referencias a wfx-docs o el título «docs: dependency audit notes».
  2. Audita los permisos de cuentas colaboradoras, exige autenticación multifactor resistente a phishing —como llaves físicas o passkeys, que explicamos en nuestra guía sobre qué son las passkeys y cómo activarlas— y revisa si ha habido ejecuciones inusuales en GitHub Actions.
  3. Si detectas actividad sospechosa, rota de inmediato todos los secretos del repositorio, tokens de acceso personal y claves de nube o APIs de IA, y limita los permisos por defecto de GITHUB_TOKEN a solo lectura siempre que sea posible.

Por qué importa

El incidente demuestra que los entornos de integración continua son un objetivo prioritario: basta comprometer la cuenta de un desarrollador con permisos de escritura para extraer credenciales de producción de toda una organización, sin necesidad de explotar un fallo en el servidor de GitHub. Este tipo de campañas automatizadas refuerzan la importancia de proteger el acceso a cuentas críticas y revisar la higiene de credenciales, un tema que también tratamos en contraseñas y passkeys y en la reciente brecha mediante agentes de IA en Chainalysis.

Qué falta por saber

  • El origen inicial exacto con el que se obtuvieron las credenciales de las 4.837 cuentas de GitHub: los informes apuntan a credenciales previamente filtradas o robadas, sin detallar un único vector.
  • El volumen total de claves de nube, tokens de acceso y secretos de APIs de IA que llegaron a ser exfiltrados y reutilizados antes de que los equipos afectados pudieran rotarlos.
  • Si GitHub introducirá controles adicionales automáticos sobre cuentas comprometidas que abren pull requests masivas contra repositorios con flujos de Actions activos.
