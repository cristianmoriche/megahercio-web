Apache corrige una vulnerabilidad RCE crítica en HTTP Server (CVE-2026-119618)

El proyecto Apache ha publicado la versión 2.4.71 de Apache HTTP Server el 11 de noviembre de 2026 para corregir CVE-2026-119618, una vulnerabilidad crítica de ejecución remota de código con puntuación CVSS 9.8 en el módulo HTTP/2.

Edición y revisión: Cristian Moriche · Publicada el 12 de noviembre de 2026 a las 18:57

Texto elaborado con ayuda de inteligencia artificial a partir de las fuentes citadas. Política editorial

Claves

  • El fallo afecta a Apache HTTP Server de la versión 2.4.55 a la 2.4.70 (y a mod_h2 independiente de 2.0.8 a 2.0.42) cuando HTTP/2 está activo.
  • Es una condición de carrera en assign_headers() de mod_http2 que permite corromper memoria heap y ejecutar código sin autenticación.
  • Investigadores de Anthropic (OSS Scanner) y Google Cloud descubrieron el error de forma independiente; urge actualizar a la 2.4.71.

Qué ha pasado

Apache publicó el 11 de noviembre de 2026 la versión 2.4.71 de Apache HTTP Server para corregir una vulnerabilidad crítica registrada como CVE-2026-119618, con una puntuación de gravedad CVSS 9.8 sobre 10.

El fallo reside en el módulo mod_http2, concretamente en la función assign_headers(), y afecta a las versiones 2.4.55 hasta 2.4.70 (así como a las entregas independientes de mod_h2 entre la 2.0.8 y la 2.0.42). Según el registro oficial de CVE y SecurityWeek, fue detectado de manera independiente por Anthropic OSS Scanner y por investigadores de vulnerabilidades de Google Cloud.

Publicidad

Cómo funciona y a quién afecta

La vulnerabilidad consiste en una condición de carrera (race condition) por sincronización incorrecta al gestionar peticiones HTTP/2 concurrentes. Varios hilos pueden acceder a memoria compartida sin bloqueo adecuado, provocando corrupción en el heap y permitiendo a un atacante remoto sin autenticación ejecutar código arbitrario y comprometer el servidor.

Los servidores que únicamente sirven tráfico HTTP/1.1 —es decir, con HTTP/2 deshabilitado— no están expuestos a esta ruta de ejecución. La actualización 2.4.71 corrige además otros dos fallos de menor gravedad (CVE-2026-106023 y CVE-2026-109163).

Cómo protegerte

  1. Actualizar de inmediato a Apache HTTP Server 2.4.71 o aplicar el paquete parcheado correspondiente de tu distribución Linux (Red Hat, Debian, Ubuntu, Amazon Linux, etc.).
  2. Comprobar la versión instalada: en la mayoría de servidores puedes verificar qué versión responde con apache2 -v o httpd -v y revisar si el módulo http2 está cargado en la configuración.
  3. Mitigación temporal: si no puedes actualizar al momento, deshabilita HTTP/2 eliminando h2 y h2c de la directiva Protocols en la configuración global o de tus virtual hosts y reinicia el servicio para limitar temporalmente el tráfico a HTTP/1.1.

Por qué importa

Apache HTTP Server es uno de los servidores web más extendidos en infraestructuras Linux y entornos en la nube, y un fallo RCE remoto sin autenticación en HTTP/2 tiene un potencial de explotación masiva en cuanto se publiquen pruebas de concepto. El hallazgo subraya además el peso creciente de herramientas automatizadas de auditoría basadas en modelos de IA, como las usadas por Anthropic y Google Cloud, que ya están detectando fallos críticos en software base antes de que trasciendan.

En la misma semana, otros componentes esenciales de servidor y navegador han requerido actualizaciones urgentes, como el octavo zero-day de Chrome o el reciente fallo de contraseñas en OpenSSH sobre Alpine. Más alertas y parches recientes en nuestra sección de ciberseguridad.

Qué falta por saber

  • Si ya existe explotación activa registrada en internet antes de la publicación del parche: las fuentes no informan de ataques confirmados hasta la fecha.
  • Cuándo completarán todas las distribuciones Linux de soporte prolongado la publicación de sus paquetes actualizados con el parche retroportado para evitar tener que compilar la versión 2.4.71 manualmente.
  • Los detalles técnicos completos de la prueba de concepto, que suelen mantenerse restringidos durante los primeros días para dar margen a los administradores de sistemas a aplicar la actualización.
